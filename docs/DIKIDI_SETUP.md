# Подключение DIKIDI

## Что уже настроено

Основная ссылка владельца: **https://dikidi.ru/2197744**. В `src/content/booking.ts` стоят `provider: 'dikidi'` и `status: 'ready'`.

**Обновление 8 ноября:** владелец предоставил новую рабочую ссылку с включённой онлайн-записью. Она заменила прежний профиль, на котором пользователь видел ошибку. Работоспособность календаря подтверждена владельцем; автоматические тесты сайта проверяют только локальный переход. Инструмент веб-проверки не смог открыть новую страницу; живое бронирование и уведомления агентом не проверялись.

При нажатии «Записаться» клиент сразу открывает эту страницу в отдельной вкладке: без окна инструкций, обязательного копирования и собственной формы заявки. Выбор фактической услуги, времени, контакты и подтверждение остаются в DIKIDI. На исходной странице сохраняется референс; вернуться можно закрытием вкладки DIKIDI. Повторные быстрые клики по одной кнопке защищены от двойного открытия.

Для настоящего встроенного виджета нужен **код, сгенерированный вашим кабинетом**. Номер профиля `2197744` не является номером виджета. Сейчас `dikidi.widgetUrl` пуст, поэтому внешний скрипт виджета вообще не загружается. Сервис не подменён собственным календарём.

## Встроенный виджет

Официальные инструкции:

- [Добавление кнопки онлайн-записи](https://support.dikidi.net/ru/knowledge-bases/4/articles/294-dobavlenie-knopki-onlajn-zapisi-na-sajte-kompanii).
- [Получение скрипта и ссылки в DIKIDI Business](https://support.dikidi.net/ru/knowledge-bases/4/articles/295-ustanovka-vidzheta-onlajn-zapisi-dikidi-na-tilda) — действия в кабинете подходят и для этого сайта; блоки Tilda не нужны.

1. В веб-кабинете DIKIDI Business откройте «Настройки → Онлайн-запись → Виджет на сайт».
2. Создайте кнопку варианта «Запись на приём». Сформируйте код.
3. Перенесите **только значение `href`** из тега `<a>` в `booking.dikidi.widgetUrl`, без HTML и кавычек. Не собирайте ссылку вручную из ID профиля.
4. Проверьте `scriptUrl` из первого шага генератора. Поддержан официальный `https://dikidi.net/assets/js/widget_record/widget2.min.js`; домены DIKIDI и путь проверяются перед загрузкой.
5. Основную `url` оставьте для резервного перехода. При необходимости укажите другую выданную DIKIDI прямую страницу в `fallbackUrl`.
6. Пересоберите сайт и проверьте ваш реальный виджет на desktop/mobile. Сайт не меняет оформление или внутренние элементы DIKIDI.

Интеграция использует стандартные ссылки генератора и официальный обработчик кликов. `window.dikidi.*`, самостоятельно придуманные API, параметры мастера/услуги и события подтверждения не вызываются. Исходный `href` виджета сохраняется без добавления UTM. При отказе/незавершённой загрузке скрипта и при управлении с клавиатуры открывается прямая страница. Официальный виджет сам определяет подходящий для устройства способ открытия. Доступность его реального интерфейса нужно проверить после получения кода.

## Запись на конкретную услугу

DIKIDI официально предусматривает варианты «Запись на конкретную услугу» и «Запись к сотруднику на указанную услугу». Создайте нужный вариант **в веб-кабинете**, затем добавьте его готовую ссылку в `dikidi.serviceWidgets`:

```ts
serviceWidgets: {
  gel: {
    widgetUrl: '',  // исходный href конкретного виджета из кабинета
    fallbackUrl: '', // необязательно: готовая прямая ссылка того же варианта
    serviceId: '', // необязательно, справочно; не используется для сборки URL
    staffId: '',   // необязательно, справочно
  },
},
```

`gel` — ID услуги **сайта** из `src/content/services.ts`. Пустые поля оставьте пустыми до получения настоящих сведений. Не используйте синтетические номера из тестов.

При наличии соответствия общая кнопка, карточка услуги, выбранный дизайн, подбор и повторная запись используют одну логику. Если вариант для услуги не задан, открывается **общая запись**: повторный выбор услуги в DIKIDI остаётся необходимым. Сайт не сообщает, что DIKIDI уже выбрал услугу, когда это не подтверждено готовой ссылкой. Связь дизайна с услугой — это пожелание клиента, не гарантия доступности процедуры.

## Предварительный каталог

В `src/content/services.ts` подготовлены **16 процедур** в четырёх категориях: маникюр, педикюр, наращивание и дополнительные услуги. На главной — четыре позиции, остальные раскрываются блоком «Все направления ухода».

У каждой позиции `confirmed: false`. На странице явно указано, что это предварительный перечень: он не подтверждает выполнение всех процедур мастером. Цены, длительность и ID DIKIDI не заполнены. Поля `includes`/`extra` тоже требуют уточнения. После подтверждения владельцем обновите данные и поставьте `confirmed: true` только у реально доступных процедур. Непредлагаемые позиции удалите, скорректировав связанные `serviceIds` портфолио и `featuredServiceIds`.

## Референс — дополнительная возможность

Дизайн хранится в `sessionStorage` вкладки, не в базе клиентов. После выбора над страницей появится «Ваш выбор» и раскрываемые «Пожелания к дизайну — по желанию». Там можно скопировать описание и ссылку; при запрете Clipboard API появляется выделяемое текстовое поле.

Копирование не нужно для открытия записи. Сайт не заявляет, что фото или пожелания отправлены мастеру. Посетитель при желании вставляет их в комментарий/сообщение самостоятельно. Событие `booking_widget_click` означает намерение открыть виджет, `booking_outbound` — переход; подтверждённой записи эти события не означают.

## Недоступность и контакты

- `status: 'ready'` — использовать настроенные ссылки.
- `status: 'not_configured'` — подключение ещё не готово.
- `status: 'paused'` — временно приостановить онлайн-переходы.

Для двух последних состояний или некорректного URL посетитель видит «Сейчас онлайн-запись недоступна». Приоритет контактов: `booking.messengerUrl`, Telegram/VK из `contacts.ts`, затем реальный телефон. Пустые/опасные ссылки не показываются. Если контакта нет, предлагается попробовать позже и открыть контакты сайта; успешная заявка не имитируется. Предупреждения о конфигурации выводятся только в консоль development.

## Что настроить владельцу в DIKIDI Business

- Подтверждённые услуги, их состав, цены и длительность; необходимые интервалы между визитами.
- Реальных специалистов, рабочий график и доступные интервалы.
- Доступность услуг для онлайн-записи и правила подтверждения.
- Уведомления о новых бронированиях мастеру и напоминания клиенту.
- Правила отмены, переноса и возможные ограничения записи.

Тарифные и доступные возможности уточняются в вашем кабинете; сайт не подключает платные функции и не отправляет уведомления самостоятельно.

## Проверка и границы тестирования

Команды: `npm test`, `npm run test:e2e`, `npm run test:a11y`, `npm run test:visual:quick`, `npm run test:full`.

Unit проверяют выбор ссылок, соответствия, безопасные домены, недоступность, контакты и отсутствие выдуманных параметров. Браузерные тесты проверяют все реальные кнопки сайта с **локально перехваченным переходом на точный URL**; сетевые запросы в DIKIDI не отправляются. Отдельный изолированный harness проверяет готовые/неверные настройки, загрузку/отказ скрипта и выбор синтетических виджетов. Его скрипт — заглушка контракта открытия, без календаря, аккаунтов или имитации подтверждённой брони. Остальной внешний трафик по-прежнему блокируется.

HTTP-проверка основной ссылки не доказывает доступность конкретной услуги или завершённого бронирования. Живой путь до подтверждения, реальные виджеты, доставка уведомлений и переносы нужно проверить владельцу в DIKIDI после настройки кабинета. Тесты не создают визитов и не используют данные клиентов.
