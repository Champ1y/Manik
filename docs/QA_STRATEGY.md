# Стратегия контроля качества

## Уровни и частота

1. `npm test`: чистая логика, схемы контента, URL/UTM, публикация. Существующий node:test сохранён.
2. `npm run test:quick`: unit + 5 Chromium smoke-сценариев, включая мобильный путь. Статический build автоматически предшествует браузеру. Обычная разработка, без полной матрицы.
3. `npm run test:visual:quick`: только Chromium на 375/768/1440 px после значимых изменений UI.
4. `npm run test:full`: lint, types, unit, build, полные E2E Chromium/Firefox/WebKit, axe, визуальные 320/375/390/768/1024/1440/1920 px. Перед крупным изменением/выпуском; отдельно по запросу.
5. `npm run check:release`: самостоятельный барьер готовности контента, сейчас ожидается exit 1. Не включён как требование успешности demo QA и не обходится.
6. `npm run test:stress:reload`: отдельная диагностика немедленного reload во время pending prefetch, 10 повторов в WebKit. В обычном persistence-сценарии навигация сначала завершается (targeted networkidle перед reload). Известная ошибка стресс-сценария не считается исправленной благодаря успешности обычного набора и не подавляется в диагностике.

Один статический build на запуск Playwright, не на каждый тест. Полная матрица браузеров относится к функциональным сценариям; screenshots/axe запускаются в Chromium, без размножения всех состояний на все браузеры.

## Изоляция и достоверность

Каждый тест получает новый browser context; никакого общего storageState/аккаунтов. Только loopback 127.0.0.1:4175, отдельный порт и запрет reuseExistingServer исключают случайный устаревший сервер. Сборка всегда свежая. Переход на точный настроенный профиль DIKIDI и явно объявленные widget/contact stubs исполняются через локальный fulfillment, без сетевого обращения к провайдеру. Необъявленные внешние запросы блокируются и считаются ошибкой. Намеренный отказ скрипта отмечается в `expectedFailures` и проверяется отдельным негативным сценарием; неожиданные ошибки не исключаются. Работающий сторонний сервис не требуется.

Контентные фикстуры — имеющиеся демо-данные. Синтетические HTTPS URL/UTM/согласие используются в unit и изолированном booking harness. Он собирает настоящий AppProvider/BookingButton, но подставляет конфиг и заглушку контракта клика по официальной ссылке. Заглушка не изображает реальный DIKIDI, календарь или подтверждённую запись. Clipboard/Web Share/storage подменяются в отдельных тестах для ошибок/успеха. Ни сообщений, ни бронирований, ни платежей тесты не создают.

Нет БД и клиентских записей — подготовка аккаунтов, seed/reset БД и очистка клиентов NOT APPLICABLE. Не создавать фиктивную серверную успешность.

Автоматическая fixture фиксирует JS exceptions, console.error, неуспешные запросы, HTTP >=400 и внешние обращения. Отмена префетча/навигации браузером допускается. Негативный HTTP 404 проверяется отдельно через APIRequestContext и recovery-страницу.

## Устойчивость

Локальные шрифты, ru-RU, Europe/Moscow, light, reduced motion, фиксированная высота/ширина; visual фиксирует время и ожидает fonts.ready. Используются роли/названия и web-first assertions, без sleep. Timeout действия 5 s, навигации 15 s, теста 30 s; более длинные инвентаризация/visual имеют обоснованный отдельный лимит. Retry 0: ошибки не скрываются повторными зелёными попытками.

Screenshots строго сравнивают пиксели (threshold 0, maxDiffPixels 0), а layout проверяет document.scrollWidth. Различия шрифтов/ОС требуют отдельных снимков платформы. Изменение на несколько пикселей будет FAIL сравнения, но продуктовый дефект подтверждается только утверждённым правилом/образцом. Автоматическое отсутствие overflow не доказывает отсутствие всех наложений — нужна визуальная проверка.

Windows WebKit по умолчанию пропускает ссылки при Tab. Первый Tab к skip-link проверяется в Chromium/Firefox; в WebKit проверяется явный фокус и активация Enter, затем клавиатура диалога. Ограничение записано как annotation, не выдано за полный тест естественного порядка Tab в WebKit.

## Эталоны

Первый набор — **кандидаты, не утверждённый дизайн**. Команда `test:visual:candidates` добавляет только отсутствующие снимки. Обычные quick/full/visual имеют `updateSnapshots: none`; отсутствие эталона — FAIL, никогда автоматическое принятие.

Снимки хранятся в `tests/visual/__screenshots__/<platform>/` и версионируются. Перед принятием просмотреть PNG/диффы, зафиксировать согласованную причину в QA_REPORT. Для намеренного изменения запускать точный `--grep`/`--update-snapshots=changed` вручную только после проверки причины; не обновлять весь набор для сокрытия ошибки. При переходе Playwright/ОС пересмотреть кандидаты отдельно.

## Отчётность и автоматизация

Каждый запуск quick/full создаёт отдельный каталог `.artifacts/qa/<UTC-id>-<mode>/`: logs, Playwright JSON/HTML, attachments, screenshot/trace при ошибке. Отображаемая дата в отчёте — Europe/Moscow; UTC в техническом имени каталога. `docs/QA_RESULTS.md` — последний автоматический прогон; `docs/QA_REPORT.md` — анализ, ограничения и исправления. История сохраняется в .artifacts, не в Git. Для передачи артефакты нужно приложить отдельно.

`test:watch` — реальный opt-in процесс для unit при сохранении. `test:ui` — интерактивный выбор/повтор браузерных тестов. AGENTS.md требует проверки будущих изменений. GitHub remote есть, существующего Actions workflow нет; удалённый CI не активирован и не заявляется выполненным. Никакие push/hooks, меняющие настройки пользователя, не выполняются.

Статусы: PASS — выполнено успешно; FAIL — выполнено с нарушением; BLOCKED — применимый сценарий невозможно выполнить (например, URL записи пуст); NOT TESTED — не запускалось/не покрыто; NOT APPLICABLE — отсутствует в архитектуре. Скрытые контентом ветви, включённая Метрика, многофото, runtime error/loading и внешнее подтверждение требуют отдельной проверки при их появлении.
