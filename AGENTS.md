## Обязательные проверки качества

- Перед изменением изучи затронутые функции и существующие тесты. Карта: `docs/PROJECT_MAP.md`, сценарии: `docs/FEATURE_MATRIX.md`, команды: `docs/TESTING_GUIDE.md`.
- Для новой функции обнови соответствующие тесты. Для исправленного воспроизводимого дефекта добавь регрессионный тест.
- После изменений запускай относящиеся тесты. Маршруты требуют проверки навигации; формы — валидации и отправки, если они существуют.
- При изменении записи проверяй выбор услуги/референса, безопасный внешний URL и честное отсутствие подтверждения. Собственный backend, календарь, конфликты и права доступа сейчас NOT APPLICABLE; не создавай их ради тестов.
- После CSS/компонентов/макетов выполни уместные адаптивные и визуальные проверки. `npm run test:visual:quick` проверяет 375/768/1440 px; полная матрица нужна перед крупным выпуском, а не после каждого сохранения.
- Перед завершением существенной задачи выполни lint, typecheck, модульные тесты, сборку и относящуюся браузерную регрессию. `npm run test:full` объединяет проверки, включая сборку через Playwright webServer.
- Не утверждай PASS без настоящего запуска. Различай PASS, FAIL, BLOCKED, NOT TESTED и NOT APPLICABLE. Указывай существующие ошибки, причину, непроверенные сценарии и ограничения окружения.
- Записывай результаты и исправления в `docs/QA_REPORT.md`; автоматические результаты: `docs/QA_RESULTS.md`, логи/HTML/trace: `.artifacts/`.
- Не изменяй эталонные скриншоты ради зелёного теста. Первые снимки — кандидаты, требующие просмотра. Обновляй только явно выбранные снимки после установления причины и согласованного изменения дизайна. Обычные тесты никогда не обновляют снимки.
- Не используй реальные клиентские данные, живые записи, сообщения и платежи. Браузерные тесты работают на loopback и блокируют внешние запросы. Не обходи этот барьер ради прохождения теста.
- Постоянный контроль обеспечивают реальные команды (`test:watch`, `test:ui`, `test:quick`, `test:full`), а не обещание агента работать между сообщениями.

## Контекст проекта

Перед работой прочитай `PROJECT_STATUS.md`: в нём текущее состояние, ограничения и следующие шаги. Команды запуска и редактирование контента описаны в `README.md`, результаты прошлых проверок — в `VERIFICATION.md`. Проверяй фактические файлы и Git diff: документы могут отставать от рабочей копии.

## Завершение этапов и подсказки для коммитов

Пользователь сам делает коммиты и push. После законченного логического этапа, который имеет смысл сохранить отдельно, явно напиши пользователю **«сделай комит»** и предложи название по фактическим изменениям этого этапа.

- Не предлагай коммит после каждого небольшого действия, чтения файлов или ответа на вопрос. Повод — завершённая функция, исправление, рефакторинг, изменение конфигурации или документации.
- Используй формат `<type>(<scope>): <краткий результат>`; область необязательна. Типы: `feat`, `fix`, `refactor`, `docs`, `test`, `chore`. Название пиши по-русски, технические термины сохраняй при необходимости.
- Перед предложением посмотри статус и diff репозитория, если Git доступен. Название должно описывать сохраняемые изменения, а не повторять уже существующие коммиты. Не приписывай себе чужие правки и не включай их автоматически.
- Для содержательных изменений предложи тело коммита: что изменилось, как реализовано и почему, какие проверки действительно выполнены, что осталось. Не называй старые результаты свежими; явно отмечай невыполненные проверки.
- Обновляй `PROJECT_STATUS.md` после такого этапа: результат, ключевые файлы/решения, проверки и их дата, оставшиеся ограничения, ближайшие действия. Этот файл должен помогать другому агенту продолжить работу без истории чата. Не копируй в него весь README и не записывай секреты или персональные данные.
- В итоговом ответе давай готовое название и, когда нужно, описание в блоке текста, чтобы их можно было скопировать в Git-клиент.
- Само предложение коммита не означает, что коммит или push выполнен. Выполняй их только по отдельному явному поручению пользователя.
